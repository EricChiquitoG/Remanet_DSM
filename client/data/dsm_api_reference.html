POST/get_options

Runs provider matchmaking for a set of process-step routes and submits them to the optimizer. This is the DSM's main entry point.

Request body

{
  "Batch": 0,                           // legacy, not used by matching
  "use_case": "electric-motor",         // must exist in the use_cases collection
  "process_requirements": {
    "product_match": "IE4",
    "quantity": 22
  },
  "routes": {
    "<routeName>": {
      "<stepName>": {
        "prerequisites": ["<stepName>", "..."],
        "requirements": {
          "<attributeName>": ["<value>", "..."]   // [] or omitted = "must exist, any value"
        }
      }
    }
  },
  "starting_point": [53.0677, -8.0660], // [lat, lon]
  "optimization_mode": "forward"        // "forward" | "reverse"
}

⚠ Before you integrate

Six real quirks in the current wire format, confirmed against the live code rather than assumed — build your parsing around these, not around what the naming suggests.

1Mixed casing inside optimizationResultsJson

Solutions, SolNumber, TransportCost, ManufacturingCost, and Energy are PascalCase — those five Go struct fields carry no json tag, so encoding/json falls back to the literal Go field name. Everything around them (processID, processSequence, dagPrereqs, processName, actorID) is camelCase. Both cases appear in the same response object.

2/select_option's "ProcessID" field isn't a process ID

It's populated from UserChoice.ProcessSequence — the ordered list of step names for that route, not an identifier. Don't key off the name; check the actual array shape.

3/select_option's "sample" drops the actor's identity

The underlying Go type's uid (actor name) and location fields are unexported, so encoding/json silently omits them. Only {"Processes": [...]} reaches the wire — no actor name, no coordinates. If you need to know which actor this sample describes, it isn't in this field; cross-reference Choice.Assignments instead.

4Energy doesn't survive into the execution graph

A chosen solution's Energy (from ProcessedSolution) is never copied into ExecutionGraph or any ProcessNode — only TransportCost and ManufacturingCost make the trip. If your frontend wants to show energy consumption over the life of an execution graph, it isn't available past /select_option's immediate response.

5Coordinate order flips between endpoints

/get_options's starting_point is [lat, lon]. /new_proposal's customerLocation.coordinates is GeoJSON-standard [longitude, latitude] — the opposite order. Easy to transpose by habit; worth an explicit check at each call site.

6/products is a separate, older, motor-only model

It predates the generalized provider/capability/batch matchmaking model (use_cases, providers, capabilities, the batch-level product records those use) and was never migrated onto it. It has no cutting-tool equivalent, no notion of a batch quantity, and a fixed six-component shape (bearings/stator/rotor/housing/windings/shaft) that doesn't generalize to other product families. Treat it as a separate, legacy data source — not a view onto the same data the optimizer matches against.
